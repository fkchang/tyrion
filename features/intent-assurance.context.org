- User approved the Opus-vetted human-witness amendment on 2026-09-27. The specification baseline declares required human witnesses and whether dependent work may proceed while validation is pending. - Distinguish As/In order/I want purpose from Given/When/Then behavioral contract. Preserve both; a keyword count is not an intent-completeness test.
- Suggested minimal gate names: intent-design and intent-implementation. Reuse append-only gate notes and existing review machinery; do not build another test runner or duplicate spec-review prompts when one review can supply explicit traceability.
- Design evidence maps each intended outcome to the design response, source revision, design revision, reviewer and verdict. Missing/ambiguous intent stays unresolved rather than guessed. Approved exclusions retain the user decision and reason.
- Implementation evidence maps outcomes to executable tests, witnessed UI/CLI behavior, or explicit human/judge assessment. Classify which proof is appropriate; never substitute test-suite success for a promised user experience or claim semantic certainty from an AI score.
- Gate evidence must identify current scenario/design/implementation revisions. A relevant change makes the prior pass stale while preserving history; opted-in closure must enforce validity, not merely see a gate note of that name.
- First application can retrospectively review the then-current worker launcher as a real sample. Record this as a current review, not a fabricated earlier gate. Do not add a circular prerequisite or reopen legacy done stories automatically.
- Bounded first version: author a coverage rubric and two concrete counterexamples (tests pass but an outcome is absent; design changed after approval) before automating pass/fail bookkeeping. Human witness remains required for subjective outcomes until independent-verification policy is actually available.
- Scenario order: source/brief -> design gate -> implementation gate. Strict rigor and one batch per scenario. Existing pre-push/UAT/spec-review remain applicable, not replaced.
- Policy refinement from user: rigor and autonomy are independent axes. Proposed additional intent gates are optional at trivial/loose and required with deeper independent review at strict. This does not turn off already-required pre-push/UAT/tests. Persist selected policy before execution; changing a CLI flag cannot silently erase a required gate.
- At EVERY rigor, dark_factory requires explicit user approval of the applicable specification baseline before unattended dispatch. The baseline contains the epic scope, affected story narratives/scenarios/acceptance outcomes, and any design constraints the user approved. Agent review is not user approval. Material scope/behavior changes require renewed approval; routine implementation choices do not. Approval records need the actual user decision's provenance and baseline revision, not an agent-authored assertion of approval.
